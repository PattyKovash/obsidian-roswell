## Background:

- Source: internal review of an autogenerated PRD (no client call yet) that inaccurately described breadcrumbs as fully disabled site-wide. In fact **product pages already show a breadcrumb trail today** — the same custom logic that was patched for a duplicate-step bug in `AED-ISSUE-12485605342`. **Collection (category) pages show no breadcrumb at all.** This ticket is to close that gap — decide the desired collection-page breadcrumb behavior with the client, and implement it — plus remove a piece of confirmed dead code found during the same review.
- This is a follow-on to `AED-ISSUE-12485605342`, not unrelated new work — see `Necessary Info` for the current-state detail that ticket already established.

## Necessary Info (Design/Documentation):

- **Current state (verified in code, both repos identical unless noted):**
  - `templates/product.json` — breadcrumbs section is live (no `disabled` flag). Built by `snippets/breadcrumb.liquid`, which pulls the category path from the site's **main navigation menu** (`linklists['aed-accessories']`), not from how the shopper arrived at the page — same trail whether they clicked through categories or landed directly. Already fixed for the duplicate-step bug (`AED-ISSUE-12485605342`, commit `7246702`, merged into `release/AED-v2026.31`).
  - `templates/collection.json`, `collection.ROTAID.json`, `collection.main-collection.json`, `collection.manikins-simulators.json`, `collection.manikins-sub-template.json` — same `breadcrumbs` section is present but explicitly `"disabled": true` in each (~line 12–14, ROTAID ~line 560). Nothing renders.
  - `snippets/breadcrumb.liquid` already contains a collection-page branch (~line 18–19, ~line 262–263) — it was written to handle products, collections, and pages from the start. Enabling the section on collection templates does **not** require new breadcrumb logic, only the per-template `disabled` flag to come off, per the open scope decision below.
  - `snippets/collection-product-breadcrumbs.liquid` — a second, separate breadcrumb implementation (98 lines) that is **not referenced by any section, template, or layout file** in either repo. Confirmed dead code.
  - No `BreadcrumbList` JSON-LD schema exists anywhere in the theme today.
- **Client confirmation needed before build:** a plain-language explainer (`Current Breadcrumb Behavior - For Client Confirmation.md`) has already been drafted for the internal team to walk the client through the two ways collection-page breadcrumbs could work. This ticket should not start build until that comes back — see Clarifying Questions.
- No new design required — visual style matches the existing product-page breadcrumb, already live.

## Constraints / Scope:

- **In scope (assumed default, pending client confirmation):** enable the existing breadcrumb section on AED4Life's 5 collection templates, reusing the existing `snippets/breadcrumb.liquid` logic as-is (no rewrite). Remove the confirmed-dead `snippets/collection-product-breadcrumbs.liquid`.
- **Out of scope for this ticket:** `BreadcrumbList` JSON-LD schema (gated separately — see Clarifying Questions), any change to product-page breadcrumb behavior (already shipped and tested under `AED-ISSUE-12485605342`), and — pending confirmation — AEDShop parity.
- **No-dev alternative:** leave collection pages breadcrumb-less (today's behavior). Valid only if the client has no preference; otherwise some dev work is required either way since Shopify's native collection breadcrumb isn't wired up on this theme's collection templates at all right now.
- **Assumption:** every collection lives somewhere under the `aed-accessories` navigation menu that `snippets/breadcrumb.liquid` walks. If a collection sits outside that menu tree, its breadcrumb would silently render `Home > Collection Name` with no ancestor path (not broken, just shallower) rather than error — flagged as an edge case, not a blocker, unless the internal team's menu audit (Clarifying Questions) finds this affects a meaningful number of collections.

## Clarifying Questions:

**From the client** (send via the plain-language explainer already drafted):

1. **Collection-page breadcrumb depth: full nav category path (matches current product-page behavior) or just `Home > Collection Name`?** — *Significantly affects estimate.* The nav-path version is already what the reused logic produces for free; a simpler "just the collection name, no ancestors" version would mean deliberately suppressing part of the existing output, and a native "only show a category if the shopper actually came from it" version is a different mechanism entirely (referrer/session-based, not menu-based) and would be materially more dev + QA work. Default assumed above: full nav path, matching product pages.
2. **Is the current product-page behavior (always shows the full nav category path, regardless of how the shopper arrived) actually what the client wants, or did they expect the simpler "only if clicked through" version there too?** — *Significantly affects estimate.* If they want product pages changed, that reopens already-shipped, tested work from `AED-ISSUE-12485605342` rather than just adding to collection pages.

**From the internal team:**

3. **Does this ticket cover AEDShop too, or AED4Life only?** — *Significantly affects estimate* — roughly doubles dev + the full-catalog sweep/QA effort, and AEDShop's nav menu handle is unconfirmed to match (`aed-accessories` reads as AED4Life-specific; see `04-engineering/patterns/breadcrumb-menu-self-links.md` in the vault). Per `CLAUDE.md`, features are generally ported to both storefronts unless decided otherwise — needs an explicit decision, not an assumption, before scoping.

Default assumed above: out of scope for this ticket.

Flag to revisit only if the audit (Dev Notes) turns up a large share of collections affected — that would be the one finding here that could still swing the estimate after the fact.
