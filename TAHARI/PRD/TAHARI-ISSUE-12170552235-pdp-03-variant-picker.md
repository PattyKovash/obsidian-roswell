
## Background:

- PRD 3 of 6 for the new PDP. Depends on **PRD-01 (Scaffolding)** for the block slot. Feeds **PRD-04 (Buy Box Actions)** (selection gates whether Add to Bag or Notify Me shows) and **PRD-05 (Sticky Bar)** (mirrors the selection). Color selection is a plain link to a sibling product (see Necessary Info), so it does not need to coordinate with PRD-02 (Gallery).

## Standing Requirement: Prefer Web Components (added 2026-07-28)

**New PDP JS should be built as a web component (a real custom element,
or extending/wrapping an existing one like `<slider-component>`), not a
bare IIFE script that reaches into the DOM from outside — especially on
the PDP, where dynamic content swap/injection is a common pattern.**

This was missed once already: `assets/main-product-gallery.js` (PRD-02)
was built as a plain querySelector-and-addEventListener script, reasoned
at the time as "glue code wiring into existing web components, not new
UI" — that reasoning didn't hold up against this standing preference and
the file is being converted after the fact (see
`02-decisions/decisions.md`, 2026-07-28).

**If there's a real reason not to build something as a web component for
a specific piece of work under this PRD, STOP and explain the reasoning
to the user, then get explicit confirmation before proceeding with a
non-web-component approach.** Do not silently default to a lighter
pattern the way the gallery script did.

  - [Size select](https://www.figma.com/design/RTEarArQVMHyU8ZuXFWfKr/Elie-Tahari?node-id=1117-15214&m=dev) — a grid of square size buttons, "Size Chart" link, selected size filled dark, sold-out sizes visually distinct.
  - The compressed size/color row seen in the [mobile full PDP reference](https://www.figma.com/design/RTEarArQVMHyU8ZuXFWfKr/Elie-Tahari?node-id=1117-15129&m=dev) once scrolled belongs to **PRD-05 (Sticky Bar)**, not this ticket.
- **Hermès reference (verified live):** clicking "Select a size" opens a slide-out panel; choosing a size closes it, updates the buy box, and changes the page URL to the matching variant — without a full reload.
- **Color is modeled as separate sibling products, not a variant option.** Confirmed: clicking a color swatch navigates to that color's own product page — a normal link, not a dynamic in-page swap. This theme already has a sibling-color-product system in place (see Dev Notes); build on it rather than the variant-option swatch system.
- Size stays a true variant option on the product (as it is today) — selecting a size continues to use whatever dynamic update (price, availability, URL) the current theme already provides. This ticket doesn't change that behavior, just the size grid's markup/styling.

## Bugs from QA:

- ✅ Fixed 2026-07-30 (found/fixed while testing PRD-04's buy-box on an OOS variant, landed directly on `pdp-combined` since no PRD-03 subagent was active — flagging here since the fixed file, `assets/main-product.css`, belongs to this ticket): a currently-selected size/color option that's also out of stock silently lost its selected (black background) styling, making an unrelated in-stock option look selected instead. Root cause: `.radio__button input:checked ~ label` and `input.disabled + label` have equal CSS specificity, and `:checked` was declared *before* `.disabled` in source order — so `.disabled` always won when both applied to the same option. `theme.css`'s own core `.radio__button` rules already order these correctly (`:checked` declared last); reordered `main-product.css` to match. Note: OOS options are intentionally still selectable (not literally `disabled`), matching the existing legacy variant-picker convention (`class="disabled"` is a styling hook only, confirmed by comparing against the live legacy `main` section) — this was a pure CSS ordering bug, not a scope change.
- ✅ Fixed 2026-07-30 (found live during this pass's own deploy, before the fix reached the shared dev theme's default state): the desktop underline rewrite (item 11) accidentally re-inverted the exact ordering from the bug above — `:checked` was placed *before* `.disabled` again during the box→underline rewrite, so a selected-but-OOS size briefly lost its underline a second time. Re-verified live on the OOS test URL after correcting the order back.
- ✅ Fixed 2026-07-30 (found live): the new mobile trigger row rendered unconditionally instead of being hidden on desktop — its `display:flex` rule was declared, unscoped, *later in the file* than the `@media (min-width:768px) { display:none }` override meant to hide it, so the later unconditional rule won at all viewports regardless of media query. Both the trigger row and the desktop grid were visible simultaneously at 1440px before the fix. Restructured as one default (`display:none`) + one mobile-only override (`display:flex` inside `max-width:767.98px`) instead of two independently-ordered blocks. Re-verified live at both viewports.
- ✅ Fixed 2026-07-30 (found live): the mobile Size/Colour drawers initially opened PRD-04's own inert stub `<template>`s (`main-product-buy-buttons.liquid`, static non-interactive divs with no real `<input>`) instead of this ticket's interactive versions — `<buy-box-drawer>.openPanel()` finds the *first* DOM child matching a panel key, and PRD-04's stub is already a child at page load while this file's version is only appended afterward by `main-product-variant-picker.js`. Fixed by having that script remove any existing same-key template before appending its own. Re-verified live: the Size drawer now shows real clickable buttons and updates the variant on tap.
- ✅ Fixed 2026-07-31 (major, found live by user QA): the entire color data source this ticket was built on — `theme.sibling_products`/`theme.siblings`/`sibling_color`-style metafields (`snippets/product-siblings.liquid`'s convention) — turned out not to be what drives correct color data in this catalog. Live-checked three products (Judith Blouse: pure native multi-color option; Amina Fluid Crepe Halter Top; Brooke Silk Charmeuse Lace Trim Skirt) and found Amina and Brooke both actually use a native Color option plus `product.metafields.custom.available_colors` (a `list.product_reference` metafield, "All Other available color of product style") for link-outs — already correctly rendered by the legacy section via `product-variant-options.liquid`'s existing `picker_type=='swatch'` branch. The original assumption that Brooke needed a separate sibling-only rendering path was wrong. Root cause of the visible symptom (1 grey swatch, wrong name) was twofold: `skip_native_color_option` (a PRD-03-only addition to `product-variant-picker.liquid`) suppressed the native option's own correct rendering whenever sibling metafields resolved at all, and a `| default: sib_product.title` fallback fabricated a fake color name/swatch handle when the sibling metafields were blank. Fix: removed `skip_native_color_option` entirely (native Color option always renders like the legacy section, restyled via CSS only — same technique as the Size grid); rebuilt the mobile trigger (flat chip) and drawer (photo cards, node 1117-15203) on native option values + `available_colors` instead of sibling metafields. Re-verified live at 1440×900 and 390×844 on all three products.
