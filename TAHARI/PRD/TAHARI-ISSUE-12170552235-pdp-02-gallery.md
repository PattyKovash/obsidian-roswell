
## Background:

- New PDP product-image gallery, matched to Figma: a horizontal image filmstrip with a thumbnail rail on desktop, a swipeable carousel on mobile. The existing zoom feature is kept as-is, just repositioned to match Figma (see Necessary Info).
- PRD 2 of 6 for the new PDP. Depends on **PRD-01 (Scaffolding)** for the block slot. Coordinates with **PRD-05 (Sticky Bar)**, which reuses the active gallery thumbnail. Does not need to coordinate with PRD-03 (Variant Picker) on image-swapping — color selection navigates to a different product page rather than swapping images in place (see Necessary Info).
- Monday Ticket: [12551885142](https://roswellstudios-company.monday.com/boards/4922048779/pulses/12551885142)

## Standing Requirement: Prefer Web Components (added 2026-07-28)

**New PDP JS should be built as a web component (a real custom element,
or extending/wrapping an existing one like `<slider-component>`), not a
bare IIFE script that reaches into the DOM from outside — especially on
the PDP, where dynamic content swap/injection is a common pattern.**

This was missed once already: `assets/main-product-gallery.js` (PRD-02)
was built as a plain querySelector-and-addEventListener script, reasoned
at the time as "glue code wiring into existing web components, not new
UI" — that reasoning didn't hold up against this standing preference and
the file is being converted after the fact (see
`02-decisions/decisions.md`, 2026-07-28).

**If there's a real reason not to build something as a web component for
a specific piece of work under this PRD, STOP and explain the reasoning
to the user, then get explicit confirmation before proceeding with a
non-web-component approach.** Do not silently default to a lighter
pattern the way the gallery script did.

## Constraints / Scope:

- **In scope:** desktop filmstrip with zoom and thumbnail rail; mobile swipeable carousel with a segmented progress indicator; fast image loading; accessible/keyboard-operable.
- **Out of scope:** any functional change to zoom (keep the current zoom feature as-is; only its placement/styling is updated to match Figma); redesigning how 3D-model or video media display (existing behavior must keep working, not be rebuilt); the variant picker itself (PRD-03); any dynamic in-page image-swapping logic for color changes — color selection is a normal page navigation, not a gallery concern.
- **Alternative considered:** building a new carousel component from scratch. Rejected — the theme's existing slider already handles drag/swipe/thumbnail-selection and is already used on this exact page today; rebuilding it would be duplicated effort with no requirement asking for it.

### QA-round bugfix: desktop gallery height-runaway (found on RC preview, `preview_theme_id=155392376969`)

**Reported symptoms (screenshot-confirmed by the coordinator, then independently re-verified live via Playwright/claude-in-chrome browser tooling against the same preview URL):**
1. The desktop gallery image area rendered completely blank.
2. The thumbnail rail rendered as a vertical column pinned to the far-left edge of the page, disconnected from the gallery.
3. No zoom icon/affordance was visible.

**Root cause (confirmed via live DOM + `getComputedStyle`/`getBoundingClientRect` inspection, not just code review):** the original desktop CSS set each slide's *width* to `78%` of the gallery stage (which spans the full section width — e.g. **2560px** on the reviewer's actual desktop viewport) and derived *height* from that width via `snippets/image.liquid`'s `.image-wrapper--cover` mechanism plus an inline `padding-top: calc(1 / var(--pdp-media-height-ratio) * 100%)`. At the computed ratio (`0.67`, a normal 2:3 portrait photo — the ratio itself was never the bug), `78% of 2560px = 1997px` wide slides produced **`1997 / 0.67 ≈ 2980px`-tall slides**. Flickity sizes `.flickity-viewport` to the selected cell's real rendered height, so that ~2980px height propagated up through `<slider-component>` → `<zoom-images>` (`.main-product-gallery__stage--desktop`) → `.main-product-gallery` → `.main-product__media` → `product-info`. Confirmed live: `.main-product-gallery__thumbs` (position: absolute, `bottom: 16px; left: 16px`) measured at `x:16, y:2712` — correctly offset from its actual (correct) positioned ancestor, but that ancestor was ~2900px down an oversized page, i.e. off-screen below the fold at any normal scroll position. Same for the zoom affordance (`y:3004`) and the floating buy-box (a PRD-04 concern, not touched here, but also pushed to `y:1910` as a downstream symptom of the same bug). Only the very top sliver of slide 1 was ever inside the first viewport, reading as "blank." All 3 reported symptoms traced to this single root cause — none required a separate fix.

**Fix:** inverted the sizing model for the desktop filmstrip to be height-driven instead of width-driven, matching Figma exactly (node `1117-15023`: each slide is a fixed `480x720` box, i.e. height = 50% of the 1440px design-frame width):
- `.main-product-gallery__stage--desktop` now gets an explicit, viewport-bounded height: `height: clamp(420px, 50vw, 720px)` — reproduces Figma's `720px` height at the `1440px` design width, scales down proportionally on smaller viewports, and is capped so it can never grow unbounded on ultra-wide monitors (the actual trigger for this bug).
- Each slide is now `height: 100%; width: auto; aspect-ratio: var(--pdp-media-height-ratio, 0.67) / 1;` — width is *derived from* the fixed height, not the reverse. The inline per-slide `padding-top` calc was removed entirely from the desktop branch (`snippets/main-product-gallery.liquid`) since it's no longer needed — `.main-product-gallery__media`/`.main-product-gallery__deferred` simply get `height: 100%` from CSS and image.liquid's existing `.image-wrapper--cover` fills that via `object-fit: cover`, exactly as designed.
- Corrected two other Figma-fidelity details discovered during the same investigation (not separately reported, but directly implicated — see AC #2/#3): thumbnail size `40x40` → `32x48` (matches Figma's portrait thumb proportions) and zoom affordance `36x36` circle → `35x35` square (matches Figma's `Icon=zoom-in` component exactly, confirmed via `get_design_context`). Updated the `sizes`/`widths` attributes on both the desktop slide and thumbnail `render 'image'` calls to match the corrected box dimensions (was `900px`/`60vw` and `64px`/square widths, now `480px`/`34vw` and `32px`/portrait widths).
- **Bonus fix, found while auditing (not one of the 3 reported bugs):** mobile video/model slides (`<deferred-media>`/`<product-model>`) had no height source at all — the mobile branch never wrapped them in a `cover` box or gave them a padding-top formula (unlike the mobile image branch, which gets one for free from `image.liquid`'s plain box). They would have rendered at 0 height. Fixed by adding the same per-slide `padding-top: calc(1 / ratio * 100%)` formula directly on the `<deferred-media>`/`<product-model>` tags, mirroring the pattern `snippets/media.liquid` already uses for the live PDP.

**What this does *not* touch:** the live, currently-shipping PDP gallery mechanism (`sections/product.liquid`, `snippets/product.liquid`, `snippets/media.liquid`, and its `--pdp-media-height-ratio` formula) — CLAUDE.md's do-not-touch list covers that live mechanism specifically, and it was never modified. This fix is entirely scoped to the new, not-yet-launched `snippets/main-product-gallery.liquid`/`assets/main-product-gallery.css` built under this PRD.

**Verification limits:** root-caused and fixed via live `getComputedStyle`/`getBoundingClientRect` inspection of the actual broken RC preview deploy (browser automation, not just code review) — confirmed exactly which ancestor was oversized and by how much, and confirmed the CSS chain that would resolve it. This worktree cannot be redeployed to preview in isolation, so the fix itself was not re-verified against a fresh live deploy — that's a pending step for whoever redeploys the combined branch (the coordinator, per their instructions). Mobile was not implicated in the bug (its height is width-driven but width is always viewport-bounded there, so it can't run away the same way) and was not separately re-tested live.

  - `attributes$2.sliderOptions` is **`data-options`**, not `data-slider-options` as the PRD's illustrative markup suggested. `JSON.parse(decodeURIComponent(...))` is called on it, but since raw JSON braces/quotes/colons pass through `decodeURIComponent` unchanged (no `%` sequences), a plain raw JSON string in the attribute works directly — confirmed this is exactly what `sections/section-slideshow.liquid` already does (`data-options='{"fade": ..., ...}'`), so `main-product-gallery.liquid` follows that same established convention.
  - `selectors$3.slide` = `[data-slide]`, `selectors$3.sliderThumb` = `[data-slider-thumb]`, `selectors$3.section` = `[data-section-id]`.
  - `classes$3.isSelected` = `is-selected` (this is also Flickity's own default selected-cell class, so no manual class-toggling JS was needed for slides), `.mobile`/`.desktop` = device-specific slide classes (not used here, see architecture note above), `is-loading`/`is-initialized`/`single-slide`.
  - `attributes$2.slideIndex` = `data-slide-index` — required on every slide for `SliderComponent#slideActions()` to sync the matching thumb by index; added to every slide in both instances.
  - Confirmed (via `assets/vendor.js`, `_makeCells` → `this.slider.children`) that Flickity requires cells to be **direct children** of the element it's instantiated on. This meant the thumbnail rail had to be a *sibling* `<div data-slider-thumb-wrapper>` inside `<slider-component>` (excluded from Flickity's cells automatically since it lacks `[data-slide]`) rather than nested inside a separate slides-wrapper — and it meant `<zoom-images>` (see below) had to wrap `<slider-component>` from the *outside*, not sit between it and the slides.

**Judgment call 2 — `zoom.js`'s `.closest("product-images")` crash (found and fixed):** confirmed by reading the deployed `assets/zoom.js` (minified, no dev source exists for it) that its click handler does `t.closest("product-images").classList.contains("is-dragging")` unconditionally. The legacy PDP always has a `<product-images>` ancestor, but the new gallery is built on `<slider-component>`, not `<product-images>` — so `closest()` returns `null` and `.classList` throws a `TypeError` on the very first click, before zoom can open. Considered wrapping the new gallery in a literal `<product-images>` tag purely for `.closest()` compatibility, but rejected it: `customElements.define('product-images', ProductImages)` in `theme.dev.js` would auto-attach the *real* `ProductImages` behavior (drag handlers, `media--active`/`media--hidden` fade logic, its own scroll-based progress bar) the moment that tag exists in the DOM, which would actively fight `<slider-component>`'s Flickity transform-based layout. Instead made the minimal, semantics-preserving fix directly in `zoom.js`: `t.closest("product-images")?.classList.contains("is-dragging")`. On the legacy PDP (ancestor present), behavior is byte-for-byte identical. On the new gallery (no ancestor), `?.` short-circuits to `undefined` → `!undefined` is `true` → zoom opens normally, which is correct since there's no drag state to guard against outside `<product-images>`. This is the exact class of "wiring fix, not functional change" the PRD pre-authorized. Editing this file was a deliberate, scoped exception to "don't touch shared/dist assets" — justified because it's a two-character change fixing a real crash, there's no dev source to edit instead, and the fix is a no-op everywhere `<product-images>` still exists.

**Judgment call 3 — segmented progress bar (a small new JS file was genuinely needed):** checked first, per Dev Notes, whether the theme's existing `data-slider-progress`/`data-slider-progress-fill`/`data-slider-counter` markup (used in `snippets/product.liquid` ~line 231) could be reused via markup alone. It cannot: that mechanism is implemented entirely inside the legacy `ProductImages` class (`theme.dev.js` ~line 6619, `this.progressFill = this.querySelector('[data-slider-progress-fill]')`), which only exists on `<product-images>`-based markup and produces a single continuous-width fill bar, not discrete segments — it has no relationship to `<slider-component>`/Flickity at all. Built `assets/main-product-gallery.js` instead (small, ~50 lines): listens for `theme:slider:loaded` (bubbles, dispatched by `SliderComponent`), then hooks `slider.flkty.on('change', index => ...)` directly (Flickity's own event, per Dev Notes' explicit suggestion) to toggle `.is-active` on discrete `<span data-gallery-progress-segment>` elements (styled via CSS `flex` row, not `repeating-linear-gradient`, for simplicity) — CSS-only segment styling, JS only toggles which one is active. The same file and the same `change` listener also drive `aria-current` syncing on the desktop thumbnail rail (AC #2's screen-reader requirement — `SliderComponent` toggles `is-selected` visually but never touches ARIA), since both gaps are solved by the same event.

**Zoom scoped to the desktop instance only (a necessary consequence of the dual-instance architecture, documented explicitly):** `data-zoom-image`/`data-image-src`/`data-image-width`/`data-image-height` attributes are only present on the desktop slide markup, not the mobile duplicate. Wrapping a single `<zoom-images>` around *both* instances would make `this.images = this.querySelectorAll('[data-zoom-image]')` pick up both the desktop and mobile copies of every photo simultaneously, producing a PhotoSwipe gallery with every image duplicated. Scoping to desktop only avoids that bug and matches Figma (the mobile mockup shows no magnifier affordance). This does mean a mobile tap on the image no longer opens zoom, which is a narrow, deliberate behavior difference from the legacy single-DOM-list gallery, made necessary by the architecture PRD-02 itself specifies (separate device-specific slide sets) — flagging this explicitly for QA/product sign-off rather than treating it as self-evidently in scope for "zoom behavior unchanged."

**First-image eager-loading tradeoff:** desktop's first slide is `loading="eager" fetchpriority="high"`; mobile's first slide is `loading="eager"` only (no `fetchpriority` override). Because both instances render on every pageview (one hidden via CSS `display: none` per viewport), marking both `fetchpriority="high"` would double the number of high-priority hero-image fetches on every load. Accepted a small, bounded cost (one duplicate `loading="eager"` image, first slide only — every other slide stays `lazy`) rather than adding viewport-detection complexity for v1.

**3D-model/video parity:** `deferred-media`/`product-model` markup, `data-deferred-media-button`, and the `<template>`-based lazy-mount pattern were copied structurally from `snippets/media.liquid` (~lines 78–123) into both slide branches, unchanged in behavior. `model_viewer_tag`'s `image_size: '1024x1024'` param (present in the original, easy to miss) was initially dropped during a first pass and caught/corrected before commit to preserve exact parity with the legacy poster-image size.
