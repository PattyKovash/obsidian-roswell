## Standing Requirement: Prefer Web Components (added 2026-07-28)

**New PDP JS should be built as a web component (a real custom element,
or extending/wrapping an existing one like `<slider-component>`), not a
bare IIFE script that reaches into the DOM from outside — especially on
the PDP, where dynamic content swap/injection is a common pattern.**

This was missed once already: `assets/main-product-gallery.js` (PRD-02)
was built as a plain querySelector-and-addEventListener script, reasoned
at the time as "glue code wiring into existing web components, not new
UI" — that reasoning didn't hold up against this standing preference and
the file is being converted after the fact (see
`02-decisions/decisions.md`, 2026-07-28).

**If there's a real reason not to build something as a web component for
a specific piece of work under this PRD, STOP and explain the reasoning
to the user, then get explicit confirmation before proceeding with a
non-web-component approach.** Do not silently default to a lighter
pattern the way the gallery script did.

## Fix Pass Scope (added 2026-07-29, after first live review)

The build above was never live-verified before this pass (see Implementation Notes' original "Not verified in this environment" note) — the user has now reviewed it live and flagged real issues. This section documents what was found and the agreed direction, to be implemented as a fix pass on top of the existing build, not a rebuild.

- **Real bug: `variant--soldout` never applies for a URL-preselected OOS variant.** Add to Bag correctly gets `disabled` server-side, but the class that swaps in the sold-out/Notify-me row never fires, so the wrong row (`--available`) stays visible. Root cause not yet diagnosed — needs investigation into whatever's supposed to add this class on load for a pre-selected variant, not just on a user-driven variant change.
- **Klaviyo's own onsite back-in-stock widget is live and conflicting with the theme's own `<klaviyo-bis-form>`.** Confirmed via live network/DOM inspection: Klaviyo's official `onsite.js` script (loaded via `static.klaviyo.com/onsite/js/klaviyo.js?company_id=UQJBK3`, unrelated to any theme code — grepped the whole repo, nothing references it) auto-detects the real `button[type="submit"][name="add"]` inside `form[action="/cart/add"]` (the standard Shopify Add to Bag button, on ANY Shopify theme) and force-hides it via inline `style="display:none !important"`, then injects its own competing "NOTIFY ME WHEN BACK IN STOCK" button into a fixed-ID container, `#klaviyo-bis-button-container`, styled with Klaviyo's own default CSS — nothing like Figma's clean black square.
  - **This is not a new problem — the old/live product page already solved it.** `assets/product.css:927` has `/* Hide default Klaviyo button */ #klaviyo-bis-button-container { display: none; }`, added in commit `e72eae0`, still live in production today. Confirmed live on the actual published theme (`role: "main"`, not preview) that this rule is what makes only the theme's own "Notify Me" button visible there. The new PDP's `assets/main-product-buy-buttons.css` never picked up this rule — that's the actual gap, not a Klaviyo dashboard/merchant-side problem.
  - **Agreed fix, not yet implemented:** since Klaviyo's real-button detection can't be defeated (it targets the standard `name="add"`/`type="submit"`/`/cart/add"` convention every Shopify theme uses, confirmed live), don't fight it on the real button. Instead: (1) port the `#klaviyo-bis-button-container { display: none; }` rule into the new PDP's own CSS as a baseline, AND (2) build the visible "Sold Out" indicator as a separate, deliberately non-targeted element — NOT `type="submit"`, NOT `name="add"`, NOT inside the `/cart/add` form — so it can never be found/hidden by Klaviyo's script regardless of the CSS port. The real Add to Bag button can stay disabled and hidden when sold out; it was never meant to be visible in that state anyway. Show/hide between {real Add to Bag + Buy Now} and {mock Sold Out indicator + theme's own Notify Me} is driven by the same variant-availability mechanism as AC6 — once the `variant--soldout` bug above is fixed.
- **Notify Me moves into a drawer, both desktop and mobile.** No desktop Figma design exists to inline the email-capture form (it currently renders inline and "looks weird" per live review) — for now, Notify Me opens in a drawer/bottom-sheet on both breakpoints. This is the first fix to implement.
- **Drawer architecture decision (2026-07-29):** the theme's only existing reusable drawer, `PopupComponent` (`theme.dev.js`, native `<dialog>`-backed, used for the size guide, cart drawer's underlying dialog, product notification popup, password page, pickup availability), slides in from the **right side at every viewport** — there's no bottom-sheet variant anywhere in the theme. Figma's mobile color/size/notify-me screens all show a top drag-handle, the standard bottom-sheet affordance — a real mismatch, not something `PopupComponent`'s existing CSS can absorb.
  - **Decision: build one new shared drawer/bottom-sheet shell**, not three separate drawer instances and not a forced fit into `PopupComponent`'s CSS. Reuse `PopupComponent`'s open/close/`<dialog>`/focus-trap *behavior* conceptually (don't duplicate that logic three times), but compose new markup/CSS for a bottom sheet with a drag-handle, since Figma's screens clearly want one.
  - **Reusability requirement:** build with an eye toward future reuse on the PLP quick-add (not in scope to build now — don't build it, just don't paint into a corner). One shared shell that Notify-me/Color/Size panels plug into gives PRD-05 and any future PLP quick-add drawer one thing to reuse instead of three.
  - Other drawer-adjacent components found and NOT the right fit: `header-drawer` (mobile-menu-specific), `cart-drawer` (its own bespoke class, not `popup-component`-based).
- **Sequencing:** update this PRD/prompt first (this section), then start with the Notify Me drawer (both breakpoints) before the color/size drawers or the Klaviyo mock-button fix.

## Dev Notes:

- **New files (proposed):** `snippets/main-product-buy-buttons.liquid` (fills PRD-01's `buy_buttons` block), a new reusable `<buy-now-button>` custom element (`assets/buy-now-button.js`). Reuse as much of `snippets/product-buttons.liquid`'s Add-to-Cart/error/back-in-stock wiring as possible.
- **Why "Buy Now" is custom, not Shopify's native dynamic checkout button:** Shopify's native dynamic-checkout button (and the newer Storefront Web Components `buyNow()` method) creates an isolated single-item checkout that drops whatever else is in the cart. Confirmed by pulling Horizon's `blocks/accelerated-checkout.liquid` directly — it's just a wrapper around that same native `payment_button` filter, so it isn't a usable reference for this requirement. The correct pattern: `POST /cart/add.js` (additive, doesn't clear the cart), then redirect to `/checkout` client-side once the add succeeds. A hidden `return_to="/checkout"` field on the same form is the no-JS fallback (still supported by Shopify's `{% form 'product' %}` tag).

```html
<buy-now-button data-variant-id="{{ current_variant.id }}">
  <button type="submit" form="product-form-{{ section.id }}" formaction="{{ routes.cart_add_url }}">
    {{ 'products.product.buy_now' | t }}
  </button>
  <input type="hidden" name="return_to" value="/checkout">
</buy-now-button>
```

```js
class BuyNowButton extends HTMLElement {
  connectedCallback() {
    this.form = this.closest('form');
    this.button = this.querySelector('button');
    this.form?.addEventListener('submit', this.onSubmit.bind(this), { capture: true });
  }
  async onSubmit(event) {
    if (event.submitter !== this.button) return; // don't intercept Add to Bag's submit
    event.preventDefault();
    this.button.disabled = true;
    this.button.classList.add('is-loading');
    try {
      const response = await fetch(window.Shopify.routes.root + 'cart/add.js', {
        method: 'POST',
        headers: { Accept: 'application/json' },
        body: new FormData(this.form),
      });
      const data = await response.json();
      if (data.status) throw data;
      window.location.href = window.Shopify.routes.root + 'checkout';
    } catch (error) {
      this.button.disabled = false;
      this.button.classList.remove('is-loading');
      this.dispatchEvent(new CustomEvent('buy-now:error', { bubbles: true, detail: error }));
    }
  }
}
customElements.define('buy-now-button', BuyNowButton);
```

- **`assets/theme.dev.js` changes (both additive, both required to make two `type="submit"` buttons in one shared `<form>` work correctly — see rationale below):**
  1. `<klaviyo-bis-form>` gained the `data-always-open` opt-in attribute the Dev Notes asked for: when set, the component starts in its `is-open` state on `connectedCallback()` (email field visible immediately) and `resetForm()` no longer collapses it back closed. `snippets/product-buttons.liquid`'s existing usage never sets this attribute, so its default two-step click-to-reveal-then-submit behavior is byte-for-byte unchanged.
  2. `ProductForm.onSubmitHandler` gained a one-line guard: `if (evt.submitter?.closest('buy-now-button')) return;` before its existing `evt.preventDefault()`. **Why this was necessary (not just "nice to have"):** the PRD's Dev Notes sketch has `<buy-now-button>` register its own `submit` listener on the shared `<form>` with `{ capture: true }`, apparently assuming that guarantees it runs before `ProductForm`'s listener. That assumption is wrong — per the DOM spec, listeners registered on the *same target element* run in registration order regardless of the capture flag, and `<product-form>` (the ancestor custom element) always upgrades/connects before `<buy-now-button>` (its descendant), so without this guard, `ProductForm.onSubmitHandler` would unconditionally `preventDefault()` and dispatch the normal `theme:cart:add` add-to-cart flow *before* `<buy-now-button>` ever got a chance to check `event.submitter` — meaning a Buy Now click would silently behave like a second Add to Bag click (no checkout redirect), and if `<buy-now-button>`'s own handler also ran afterward, it could double-add the item. The guard is additive and no-op for every existing form in the theme, since none of them contain a `<buy-now-button>` element.
- **Judgment call — reconciling the "always-open" Dev Note with AC6/AC7 (flagging this clearly, did not block on it):** the Dev Notes say to make `<klaviyo-bis-form>` "render with the email field already visible on `connectedCallback()`... instead of its current two-step click-to-reveal behavior," which read literally would mean the email field is visible immediately whenever the sold-out state renders. But AC6 explicitly requires a compact disabled-"Sold Out"-plus-solid-"Notify me"-button pairing first, and AC7 explicitly requires that *clicking* "Notify me" is what reveals the email form — both directly confirmed against Figma screenshots (nodes 1117-15129 and 1117-15227 are two visually distinct states, not one). Implemented it as: the compact pairing is plain markup (not `<klaviyo-bis-form>` at all) with its own lightweight toggle button; clicking it reveals a separate `<klaviyo-bis-form data-always-open>` panel. This satisfies the AC's click-to-reveal requirement *and* gives real, working meaning to `data-always-open` (its own internal open/close toggle is skipped — so once revealed, one click on the panel's own button submits, instead of the component's old default of needing a first click to open and a second to submit). This also means `data-always-open` is real, tested, reusable functionality if PRD-05 or a future standalone signup surface wants a form that's open from first paint with no reveal step at all.

## Bugs from QA:

- ✅ Fixed 2026-07-30: `variant--soldout` never applied on a URL-preselected OOS variant. Root cause: `snippets/main-product-buy-buttons.liquid` gated the class (and the "Sold Out" button text) on `variant_unavailable and onboarding_product == false`, where `onboarding_product = product.empty?`. For a real product `product.empty?` returns `nil`, not the literal boolean `false` — and Liquid's `==` treats `nil` and `false` as unequal (even though both are falsy for truthiness checks), so the whole condition silently evaluated `false` regardless of `variant_unavailable`. The submit button's own `disabled` attribute used a separate, simpler `{% if variant_unavailable %}` check with no such comparison, so it worked while the class/text didn't — that asymmetry was the tell. Fixed by changing both checks to `onboarding_product != true`. Confirmed the identical bug pattern pre-exists in the **old, live** `snippets/product.liquid:312` — out of this ticket's scope, flagged separately, not fixed here.
- ✅ Fixed 2026-07-29/30: a Liquid syntax error (`current_variant.options[color_option.position | minus: 1]` — filters aren't allowed inside `[]` indexing) was silently killing the *entire* `buy_buttons` block render on every product. This meant AC1–12 had never actually rendered live on any tested product before this pass, despite being marked ✅ Dev. Fixed by precomputing the 0-based option index via `assign` before the loop.
- ✅ Fixed 2026-07-30: mobile Notify Me drawer panel didn't match Figma (node 1117-15227) — text was centered instead of left-aligned, heading font-size used `var(--font-body-regular)` which is never defined anywhere in the theme (silently fell back to inherited size), and the panel had no minimum height so the email field sat right under the heading instead of pushed toward the bottom of a 376px content area via a flex spacer. Also: the theme's root font-size is 14px, so none of the existing `--font-body-*` rem tokens land on Figma's literal 16px spec — hardcoded `font-size: 16px` instead of forcing an imprecise token match.
- ✅ Fixed 2026-07-30: desktop Add to Bag / Buy Now used the theme's generic stretched-to-fill `.btn` layout (correct for the mobile sticky bar) instead of Figma's actual desktop spec. Confirmed via `get_metadata`/`get_design_context` on the nested node inside 1117-15023 ("Hero CTA" → Frame 272 → Frame 84 → CTA): both buttons are fixed 88×88px squares, 10px padding, text top-left aligned (not centered), 12px MAC06 Regular (not bold/uppercase), no gap between them. Added a `min-width: 750px` override in `assets/main-product-buy-buttons.css` scoped to desktop only — mobile's stretched-button treatment (sticky footer bar, not yet built) is unaffected.
- ✅ Fixed 2026-07-30: the available-row buttons rendered flush-left while the sold-out row rendered flush-right — inconsistent with each other, caught via live spot-check. Root cause: `.buy-box-actions__form` is its own nested flex context, one level deeper than `.buy-box-actions` (it wraps the buttons inside `<product-form>`), so the outer `justify-content: flex-end` never reached through to it. **First fix attempt (superseded same day):** added `flex-end` on `.buy-box-actions__form` too, matching Figma's Hero CTA card reference, which right-aligns its button row. **Corrected per explicit user direction:** the Hero CTA card is a floating marketing card, not this page's actual layout — every other row in the real PDP form (title, color, size) is left-aligned, so the buttons should be too. Removed the `flex-end` override entirely; `flex-start` (the default) is now correct and consistent on both rows.
- ✅ Fixed 2026-07-30: `<buy-now-button>` stayed disabled after switching from an OOS variant back to an in-stock one. Root cause: `product-info.js`'s `handleUpdateProductInfo` (shared file, unmodified) only knows to toggle Add to Bag's submit button via `ProductForm.toggleSubmitButton()` — `<buy-now-button>` didn't exist when that flow was built, so its own `disabled` state was only ever set once, at initial server render. Fixed inside this ticket's own `assets/buy-now-button.js` by subscribing to the same `theme.PUB_SUB_EVENTS.variantChange` pub/sub event `assets/main-product-buy-buttons.js` already listens to (no shared-file changes needed) and syncing `button.disabled` to `!variant || !variant.available` on each change.
